## What this covers

The bundle run left two claims unchecked, and both are the kind that only fail
against a real server.

**A layer chip has to be honest.** The chip list is derived on the client and
the permission is enforced on the server, so they are two answers to one
question. A chip that offers a layer the route then refuses is worse than a
missing chip: it looks like it worked.

**A transport decides which fields exist.** An MCP server reached over stdio and
one reached over SSE share nothing but a description. Showing a command and a
URL together makes "which of these did they mean" a question the reader has to
answer from the values.

## Setup done outside the browser

Creating a root organisation is a master-admin action, and what is under test is
not who may create one. The run signs up its own account, then inserts an
organisation and a `subtree` responsibility for it directly, and reloads. Driving
this through a master account would mean knowing a password, which would mean
writing one down.

Two things the setup ran into, both noted rather than fixed:

- `admin.organizations.created_at` has **no default**. Every insert path has
  always supplied it, so nothing noticed until an insert that did not.
- `psql -At -c "… RETURNING id"` prints the value and then the command tag. Read
  whole, the tag becomes part of the id — which looks right until a foreign key
  disagrees. The helper now drops tag lines.

## MCP is not in the prompt

Checked in `packages/vibeagent_domain/src/server/context/mcp.test.ts` rather than
here, because it is a claim about what is composed, not about what a screen
shows: with a skill bound to an SSE server carrying a bearer token, the rendered
suffix contains the skill's name and none of the server's name, host, or
credential.

At runtime the servers are stored in `vibe_session.mcp_servers`, written in the
same statement as the prompt and under the same once-only guard. A session whose
servers were settled at a different moment from its instructions is a session
nobody configured.

## Residual risk

- **Nothing connects to an MCP server yet.** Entries are validated, bound to the
  skills that declare them, and stored where the tool side can read them. The
  stdio process and the SSE client are not written. A skill that names a server
  today gets a correct answer to "which server" and no connection.
- **`enforced` is checked at one depth.** A root organisation's enforced entry
  beating an account's is tested in `admin_domain`; a sub-organisation trying to
  soften an ancestor's is tested there too, but not through the screen.
- The seeded organisation and the accounts each run creates are left behind.
  They are inert, but they accumulate.
