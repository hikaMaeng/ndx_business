## Part one — which layer wins

Four layers, real skills, a root organisation with a child under it and the
project running under the child.

| Case | Result |
| --- | --- |
| root enforced-off vs three nearer layers all enabled | **root wins** — `["account-project","account","organization"]` all shadowed, and the skill is absent from the index |
| root enforced, uncontested | root wins, mode `enforced` |
| root default vs child default | **child wins** — a root's default does not freeze anything |
| account default vs project default | project wins |

The first and third are the pair that matters. If only the first were tested,
a merge that always picked the root would pass. If only the third, one that
always picked the nearest would. Together they say the two modes are two modes.

The enforced-off skill being *absent* rather than listed-and-disabled is the
part worth stating: an agent offered something it cannot use will try it, and
the refusal costs a round trip to teach what an absence teaches for free.

Every surviving path was checked against the disk from inside `worker-tool` —
an index naming a folder nobody wrote is a dead end that reads as a capability.

## Part two — the execution contract

The three promises the index makes, tested against the container rather than
inferred:

| Promise | Result |
| --- | --- |
| the working directory is the project | `cwd` = `/workspace/<uid>/<project>` |
| the skill's files resolve from the script | `references/expected.txt` read from `/skills/account/<uid>/contract-check/references/` |
| the skill's folder is read-only | writing beside itself → **`EROFS`** |
| output goes to the project | `contract-report.json` landed in the project |

And the reason the prompt says to read `SKILL.md` rather than to run scripts
directly, confirmed empirically:

```
test -x .../touch-project.sh        → plain
.../touch-project.sh                → Permission denied
bash .../touch-project.sh           → done
```

A zip carries no permission bit, so an uploaded script is never executable. An
index telling agents to run `./script.sh` would be wrong for every skill anyone
uploads. It does not, and now there is a test that says why.

## What the catalogue needs, measured

The tool container was asked what it has, against what the six skills' own
instructions name:

| Command | Present | Asked for by |
| --- | --- | --- |
| `bash`, `node`, `npm`, `npx` | yes | most |
| `python3` | **was missing** | mcp-builder, skill-creator, pdf, webapp-testing, docx |
| `pip3` | no | pdf |
| `soffice`, `pdftoppm`, `pandoc` | no | docx |
| `pdftotext`, `qpdf` | no | pdf |

Five of six could not run as written. Two changes followed.

**`python3` is now in the tool image.** ~47 MB in one layer shared by all four
workers. It is there for the same reason `bash` is: skills are how capability is
added to this deployment, and a skill that cannot start is not a capability.

**Everything heavier is deliberately absent, and now visible.** A base image
that grew to cover LibreOffice, ImageMagick and a language toolchain would be
guessing at everyone's dependencies. Instead, uploading a skill reads the
commands its `SKILL.md` names and the skills screen lists them, so the gap shows
up where somebody installs a skill rather than where an agent fails to run it.

Reading them needed more care than a word search. `make`, `go` and `convert` are
ordinary English words, so only code counts — fenced blocks, indented blocks,
inline spans. And a fence's *language tag* counts too: a page of Python source
contains no `python`, so `pdf` and `webapp-testing` looked like they needed
nothing until the tag was read.

Detection on the real catalogue:

```
mcp-builder      npm npx python3
skill-creator    bash python3
pdf              bash pdftotext python3 qpdf
webapp-testing   bash npm python3
canvas-design    (none)
docx             bash npm pandoc pdftoppm python3 soffice
algorithmic-art  node
```

`canvas-design` reporting nothing is the right answer — it is fonts and prose —
and a detector that always finds something is one that has stopped meaning it.

## One finding not fixed

**Every account's folder is visible to the tool container.** `/workspace` is
mounted whole, and isolation between accounts is by composed path: the session
row holds `<uid>/<project>`, and nothing but that composition stops a command
from reading `/workspace/<other-uid>/`. The agent's one tool is bash, so this is
reachable by `ls /workspace`.

This is a property of the topology rather than a bug in it — the same mount
serves every session the worker picks up, and per-session mounts would mean a
container per session. Recorded here because it is a real limit on what
"다른 계정의 폴더는 접근할 수 없다" currently means: it is true of the paths the
system composes, and not of the filesystem the agent can see.

## Residual risk

- **`python3` alone gets very little.** Measured after the image was rebuilt, by
  parsing every real script and asking the interpreter which of its imports it
  can find: **2 of 12** start on the standard library alone. The rest want
  `pypdf`, `pdfplumber`, `pdf2image`, `PIL`, `playwright`. Having the
  interpreter is not having the skill — a script that fails on its first import
  fails exactly as loudly as one with no Python at all.

  This is the open question, and it is a design decision rather than a bug:
  a skill needs its own dependencies, and nothing here provides them. Baking
  common libraries into the image guesses at everyone.s; installing at runtime
  needs a writable cache and a network policy, neither of which exists; leaving
  it to each deployment to extend the image is honest but pushes the problem.
  The requirement list on the skills screen makes the gap visible; it does not
  close it.
- **No agent has run a skill.** The contract is proven by running a skill's
  scripts the way the prompt describes. Nothing has yet read a `SKILL.md` and
  decided to.
- **`requiredCommands` is approximate by design.** It reads code regions and
  fence tags; a skill that names a dependency only in prose will not be listed.
- The enforcement run leaves an organisation tree and an account behind.
