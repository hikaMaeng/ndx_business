## What changed

Skills are how capability is added to this deployment, so the container that
runs them now carries what published skills actually reach for, installed
globally rather than per skill. A skill's folder is read-only and a project is
not the place for a virtualenv, so there is nowhere for a skill to install
anything at the moment it needs it — and doing so would mean a network call in
the middle of a task.

**The base moved from Alpine to Debian slim.** Alpine is musl, and both the
browsers Playwright ships and much of the Python wheel ecosystem are built
against glibc. On Alpine each of those has to be swapped for a distribution
package and then pointed at by hand, which is a stream of small breakages a
skill author cannot see coming. The larger base buys one property: a skill
written elsewhere runs here.

## Verified against the container, not the Dockerfile

A Dockerfile says what was asked for; the container says what happened. Every
check below ran inside `worker-tool`.

| Group | Checked |
| --- | --- |
| shell and VCS | `bash` `git` `curl` `unzip` |
| runtimes | `node` `npm` `npx` `python3` `pip3` |
| documents | `pandoc` `markitdown` |
| pdf | `pdftoppm` `pdftotext` `qpdf` `gs` |
| images | `convert` |

Python packages were asked of the interpreter with an import rather than of pip
with `pip show`: what matters is whether a script's first line works, and a
package that is present but unimportable — a partial install, a wrong
architecture — reports fine to pip. All sixteen import: `pypdf`, `pdfplumber`,
`pdf2image`, `PIL`, `reportlab`, `docx`, `openpyxl`, `pptx`, `markitdown`,
`playwright`, `requests`, `bs4`, `lxml`, `yaml`, `markdown`, `defusedxml`.

Three checks exist because "present" and "usable" are different claims, and the
browser is where they come apart most often:

- **the browser launches** — Chromium 151.0.7922.34
- **and renders a page** — content set, title and text read back
- **the browser path is in the environment** — `/opt/playwright`, not only at
  build time. Set at build and not kept, the runtime looks elsewhere and reports
  a browser that is plainly present as missing.

And one end-to-end: a PDF written with `reportlab` and read back with
`pdftotext`. `import pypdf` succeeding says less than a file surviving the trip.

## Effect on the catalogue

The same probe that measured the gap before now measures what closed:

| | before | after |
| --- | --- | --- |
| real Python scripts starting on what the image provides | **2 of 12** | **12 of 12** |

The remaining one was a false negative in the probe rather than a missing
package: it imports a *sibling module* from its own skill folder. Python puts a
script's own directory on `sys.path` when it runs it, and the probe did not —
so it reported the file sitting next to the one it was reading as absent. Fixed.

`python` is now an alias for `python3`. A skill that writes the older name is
not making a mistake, and a symlink is cheaper than every author remembering.

Layers are cached, so this is paid once. A code change rebuilds only the last
5.5 MB layer, and deploy time is unchanged after the first build.

## The one deliberate omission

**LibreOffice (`soffice`)** — about 700 MB on its own, comparable to everything
above put together. Without it, document *creation and editing* work fully
(`python-docx`, `python-pptx`, `openpyxl`); only Office → PDF conversion does
not. `docx` is the one skill in the collected catalogue that asks for it, and it
is listed as an unmet requirement on the skills screen, which is where a gap of
this kind should show up.

## Residual risk

- **Nothing pins versions.** `pip3 install pypdf pdfplumber …` takes whatever is
  current at build time, so two builds a month apart can differ. That is a
  deliberate simplicity for now and the obvious thing to regret later.
- **The image is a shared decision.** All four workers run from it, though only
  `worker-tool` executes skill scripts. Splitting the tool runner onto its own
  image would keep the other three small; it would also double what a deploy
  builds.
- A skill needing something absent still fails at runtime. The requirement list
  on the skills screen makes that visible at install time; it does not prevent
  it.
