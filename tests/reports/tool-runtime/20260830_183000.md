## What was added, and why each

**LibreOffice** — the one thing nothing else in Debian does. Installed as
`libreoffice-core` plus writer, calc and impress rather than the umbrella
package, with recommends off: the umbrella pulls a desktop this container has no
screen for. ~700 MB, the largest single item in the image.

**A notebook kernel** — `ipykernel`, `nbclient`, `nbconvert`, `jupyterlab`.
Running Python as a series of one-shot scripts throws away every variable
between them, so anything exploratory has to reload the file, re-fit the model
or re-parse the document on each step. A kernel keeps that state, which turns
"run this script" into "keep working in the same session".

**`numpy`, `pandas`, `matplotlib`** — the trio anything analytical assumes.
**`tesseract`** with English and Korean data, **`ffmpeg`**, and the everyday
Python a script reaches for without thinking.

The Python list moved out of the Dockerfile into
`apps/vibeagent/docker/requirements.txt`. That is the list people will actually
argue about, and a list worth reviewing should be readable without reading a
build.

## Present versus usable

Command existence proves the least interesting half. Five checks exist for the
gap between a tool being installed and being usable, and each of them fails in a
way that reads as the tool's fault:

| Check | Result |
| --- | --- |
| LibreOffice converts a `.docx` to PDF and the text reads back | `office to pdf` |
| **Korean survives the conversion** | `변환 확인` — the CJK fonts are real, not boxes |
| a kernel runs two cells and the second sees the first | `45` |
| OCR reads text back out of an image made here | `RUNTIME OCR` |
| matplotlib draws to a file with no display | `Agg`, file written |

The Korean check is the one worth keeping. A conversion that "succeeds" while
rendering every CJK character as a box produces a PDF nobody can read and a
green test.

The kernel check is two cells rather than one for the same reason: a kernel that
forgets between cells is a slower way of running two scripts, and one cell
cannot tell the difference.

## Three environment variables

Each is the difference between installed and usable:

- `HOME=/home/node` — LibreOffice, Jupyter and matplotlib all want somewhere to
  write a profile. A process with no home writes to `/` and fails there.
- `MPLBACKEND=Agg` — matplotlib otherwise looks for a display. A plot here is a
  file, never a window.
- `PLAYWRIGHT_BROWSERS_PATH=/opt/playwright` — set at build and not kept, the
  runtime looks elsewhere and reports a browser that is plainly present as
  missing.

## One failure, which was the test's

The kernel check failed on its first run with a Python `SyntaxError`. The probe
was passed to `python3 -c` with its statements joined by semicolons, which
cannot hold the multi-line list literal it needed — the test reported a syntax
error of its own making as a broken kernel. Delivered through stdin as a file
instead, which is the same fix the import probe needed earlier, for the same
reason: every layer of shell quoting between here and there is a chance to
corrupt a measurement into something that looks like data.

## Residual risk

- **Nothing pins versions.** `requirements.txt` names packages, not releases, so
  two builds a month apart can differ. Deliberate for now, and the obvious thing
  to regret later — the fix is a freeze committed beside it.
- ~~One image, four workers.~~ **Split.** One Dockerfile, two targets: the four
  containers that never run a skill take `service` and the base layer, and
  `worker-tool` takes `tool`. **3.16 GB → 367 MB** for the four; worker-tool
  unchanged, and all 31 runtime checks still pass on it.

  The heavy stages sit before the code layer on purpose. Building the tool
  image on top of the finished service image would have been less duplication
  and would have put the runtime after the code — the one arrangement where a
  one-line change rebuilds a browser.

  `target: service` is named in the compose anchor rather than left to the last
  stage: without it, adding a stage to the Dockerfile silently changes what
  four containers run.
- **Still no agent has run a skill.** The runtime is proven by running the tools
  the way a skill would. Nothing has yet read a `SKILL.md` and decided to.
- `/workspace` remains mounted whole into the tool container, so isolation
  between accounts is by composed path rather than by what the filesystem shows.
