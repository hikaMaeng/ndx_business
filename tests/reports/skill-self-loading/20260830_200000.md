## The question

Everything before this proved plumbing: the index reaches the session, the files
are where it says, the container can run them. None of it touched the thing the
design rests on — that a model given **one line and a path** goes and reads the
skill when the task calls for it.

## Why the skill is deliberately arbitrary

A skill that says "make a PDF" proves nothing. The model can make a PDF without
reading anything, and a green result would only say the model is competent.

So the skill carries conventions it **cannot invent**:

| Convention | Could the model guess it? |
| --- | --- |
| write to `NOTES/release.md`, not `RELEASE.md` | no |
| first line `⟦NDX-RELEASE-NOTE⟧` | no |
| exactly `## 무엇이 바뀌었나`, `## 왜 바꿨나`, `## 확인한 것`, in that order | no |
| a stamp produced only by running the skill's own script | **not even in principle** |

The ask mentioned none of them: *"이 프로젝트의 릴리스 노트를 작성해줘. 이번
변경은 스킬 로딩 기능 추가야."*

## What happened

```
⟦NDX-RELEASE-NOTE⟧

## 무엇이 바뀌었나
스킬 로딩 기능이 추가되었습니다.

## 왜 바꿨나
사용자가 커스텀 스킬을 로드하고 실행할 수 있도록 …

## 확인한 것
- 스킬 파일이 올바르게 로드되는지 확인
- 스킬 실행 시 예상된 동작이 수행되는지 검증

stamp: ndx-mtfiisqj-marker
```

Every arbitrary requirement is met. The transcript shows the model reading
`/skills/account/<uid>/release-notes/SKILL.md` before it wrote anything, and the
stamp is there — which means it also ran `scripts/stamp.mjs` from the project
directory, exactly as the execution contract describes.

The session was given **one line** about the skill and its path, and none of the
skill's contents: the banner and the headings appear nowhere in the prompt. That
check exists because if the whole `SKILL.md` were in the prefix, the model would
not have to load anything and this experiment would be measuring nothing.

## The negative half

A model that reads every skill on every turn is not selecting, it is curious —
and the index would cost a page of attention on every conversation for nothing.

Asked `2 더하기 2는 얼마야? 파일은 만들지 마.` in the same session, it made **no
tool calls at all**. It did not revisit the skills, and it did not reach for
bash to do arithmetic.

## The finding worth keeping

The first run got one character wrong. The banner's closing bracket came back as
`⟩` (U+27E9) instead of `⟧` (U+27E7) — one glyph out of eighteen, and the rarest
one in the line. The second run reproduced it exactly.

Two runs, one drift. **Intermittent**, which is worse than consistent: it passes
a test and fails in production sometimes.

The contrast in the same file is the lesson. The stamp was byte-exact in both
runs — because the model did not copy it, it ran a script that wrote it.

> Anything in a skill that has to be exact belongs in a script, not in prose to
> be transcribed. A convention a reader copies is a convention that drifts.

The banner check now asks for the distinctive middle of the line and records the
byte-for-byte answer separately, because those turned out to be two different
questions and only one of them is a defect.

## What this does and does not establish

**Established**: a model selects a skill from a one-line index, reads it, follows
instructions it could not have invented, runs the skill's script from the
project, and leaves the skills alone when nothing calls for one.

**Not established**:

- **One model, one task, two runs.** A 30B local model on a well-specified
  task. Nothing here says how selection behaves with twenty skills whose
  descriptions overlap, which is the case that decides whether a one-line index
  scales.
- **No skill was declined.** Every run used the one skill that fit. A skill that
  *nearly* fits — where reading it and then not using it is the right answer —
  has not been tried.
- **No conflicting skills.** Two skills claiming the same task would test the
  description, and descriptions are the part this design leans on hardest.
- The negative case was one arithmetic question. A task that merely resembles a
  skill's territory is the interesting negative, and it was not run.
