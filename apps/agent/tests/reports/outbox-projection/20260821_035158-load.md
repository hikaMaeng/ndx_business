# 2,048 request / 96 worker durable-drain report

## Environment

- deployed `agent`: image `sha256:7e8f3430ba4dd9051a544a07a2135fc8ae420aa32ccc77c673ec84f6ca1f0d3e`, `/health` 200
- host CPU count: 48; `AGENT_MAX_THREADS` defaulted to 96 and the server logged `maxWorkerThreads:96`
- workload: 2,048 `test.delay` commands, 96 concurrent submitters, 512 session streams, four ingress channels, 5,000 ms worker delay
- planned lower-bound model: `ceil(2048 / 96) * 5000 = 110,000 ms`; pass budget: 125,000 ms

## Executed steps

1. Submitted a unique `delay-1787251940209-*` prefix to the deployed HTTP ingress.
2. Waited for durable job drain, outbox publication, and result-queue delivery.
3. Queried the prefix in `event_processing_job`, `event_store`, `event_outbox`, `agent_execution`, and `pgmq.q_agent_results`.
4. Deleted only rows/messages whose transaction key had that prefix, then re-queried all five ledgers.

## Reproducibility

Run the companion plan with the local metrics token and these values:

```powershell
$env:AGENT_DELAY_TOTAL='2048'; $env:AGENT_DELAY_WORKERS='96'
$env:AGENT_DELAY_STREAMS='512'; $env:AGENT_DELAY_MS='5000'
$env:AGENT_DELAY_TIMEOUT_MS='180000'; $env:AGENT_DELAY_SLO_OVERHEAD_MS='15000'
node apps/agent/tests/load/worker-concurrency.mjs
```

The interactive command host interrupts foreground processes at 30 seconds, so this run used service-side durable cardinality and database timestamps rather than the harness's final stdout. The same harness submitted the workload; all pass criteria were checked directly against the deployed persistence and PGMQ state.
