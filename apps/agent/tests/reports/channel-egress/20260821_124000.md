# Multi-channel fairness load report

## Workload

- 1,024 HTTP commands, accepted with 128 concurrent submitters.
- Four subscribed live channels, 256 commands each.
- 512 independent `sessionKey` values so the test measures multi-client throughput rather than intentional same-stream serialization.
- Latency is HTTP 202 acceptance to canonical live command receipt; submit queue time is reported separately.

## Result

| Channel | Received | p50 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: |
| `s.c0` | 256/256 | 1,950 ms | 5,153 ms | 5,253 ms |
| `s.c1` | 256/256 | 1,955 ms | 5,112 ms | 5,282 ms |
| `s.c2` | 256/256 | 1,956 ms | 5,149 ms | 5,281 ms |
| `s.c3` | 256/256 | 1,949 ms | 5,101 ms | 5,281 ms |

- Accepted: 1,024/1,024.
- Live receipts: 1,024/1,024.
- Submit elapsed: 2,766 ms; full live drain: 8,147 ms.
- The command/result jobs completed before cleanup. All `measure-*` and `measure2-*` event, processing, execution, delivery, and queue rows were removed afterward.

## Calibration

A prior four-stream run showed p95 near 11 seconds because each channel intentionally serialized 256 events on one stream. That is not representative of the multi-client workload; the independent-session run above is the acceptance result.
