2026-08-19 21:52 (local)

## Executed Steps
1. `POST /api/events` `transactionKey=verify-tx-1787143620`, payload `{input, sessionKey: verify-session-1, runKey: verify-run-1, turnKey: verify-turn-1}` → `202`.
2. Read `event.persisted` from `docker logs agent`.
3. `SELECT sequence,kind,action,event_id,causation_event_id,session_id,run_id,turn_id FROM event_store WHERE stream_id='session:verify-session-1' ORDER BY sequence`.
4. Repeated step 1 with the same transaction key and payload → `202`.
5. `SELECT kind, count(*) ... GROUP BY kind` and a count of rows in `channel:agent.results` for that key.
6. `SELECT count(*) FROM event_store WHERE stream_id LIKE 'session:%' AND session_id IS NULL`.
7. `GET /metrics` without a token, then with `Authorization: Bearer local-agent-metrics`; also `GET /no-such-route`.

## Failures
None against the plan.

Out of scope but observed: the two POSTs carry different client event IDs, so the store
holds two `command` rows for one transaction key. That is correct — they are two distinct
client submissions — and the redelivery case (same `event_id` twice) is covered by the
pre-existing `acceptance-duplicate-event-001` row, which remains a single row.

## Reproducibility
`npm run deploy agent`, then the seven steps above with any fresh `transactionKey`.
Sequences differ per run; kinds, counts, causation, and stream membership do not.
`docker exec admin psql -U postgres -d ndx_business` reaches the database.
