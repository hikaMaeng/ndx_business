# Testing

Run `npm run lint --workspace agent`, `npm run test --workspace agent`, and `npm exec turbo run build --filter=./apps/agent`. Use `npm run deploy agent` for the Compose refresh, then the health endpoint and a queue round trip for integration verification.

`tests/plans/` and `tests/reports/` hold the event-store acceptance records. Event-store behaviour that depends on PostgreSQL type mapping — `bigint` sequences arriving as text, the identity backfill, and duplicate convergence — is not provable against a stubbed pool; verify it against the deployed database and record the queries in the report.

Browser verification drives the `/ws` console at `/`. Prefer role and accessible-name locators; the shell exposes `main` as its landmark.

Run `node apps/agent/tests/load/multichannel.mjs` against a deployed token-enabled Agent for concurrency verification. It distributes requests over four channels and 40 streams, then requires zero scheduler and delivery backlog before passing. During the run, retain `/metrics`: `processingReadyOldestMs` must return to zero, `processingExpiredLeases` must remain zero, and `schedulerDispatchActive` must not exceed `AGENT_MAX_THREADS`. Set `AGENT_LOAD_TOTAL`, `AGENT_LOAD_CONCURRENCY`, and the SLO-bound `AGENT_LOAD_TIMEOUT_MS` for the intended load envelope.

Run `node apps/agent/tests/load/worker-concurrency.mjs` for the worker-parallelism proof. Its `test.delay` request waits `AGENT_DELAY_MS` (default 5,000) in the worker, returns a durable result event, and is spread across four channels and `AGENT_DELAY_STREAMS` independent sessions (default: up to 512). Set `AGENT_DELAY_TOTAL` and `AGENT_DELAY_WORKERS` to the deployed `AGENT_MAX_THREADS`; the run passes only when all result deliveries settle, no lease expires, and elapsed time is no more than `ceil(total/workers) * delay + AGENT_DELAY_SLO_OVERHEAD_MS` (default 15,000). This is deliberately separate from the high-volume hash load, which measures ingress and persistence pressure. A many-client benchmark must set enough streams to avoid measuring intentional per-stream ordering serialization instead of pool throughput.

Run `node apps/agent/tests/load/websocket-fairness.mjs` against the deployed service for channel isolation and end-to-end latency. It opens one subscriber per reply channel, requires every terminal event to reach only its designated connection, reports p50/p95/p99 from client submission to browser receipt (default p99 budget: 10,000 ms), waits for every server-side cursor advance, and rejects residual processing/outbox backlog. Keep its generated transaction prefix isolated and delete all scoped database/PGMQ rows after the run. Pair it with the mailbox/replay-buffer unit tests: a slow connection may close or drop progress, but must not raise latency for another channel.

For browser replay, first let the rendered UI establish its cursor, deliberately disconnect it, submit more than `AGENT_WEBSOCKET_REPLAY_MAX` terminal events, then restore the connection. Require exact event IDs, at least one paged `replayComplete=false` frame followed by `true`, and a successful second reconnect. Reload once after changing channels to prove a persisted cursor is not reused across a fingerprint change. Record deliberate offline browser console errors separately from page errors.

Each scheduler/deploy change also needs a real PostgreSQL lease test after deployment: claim a job, renew it after one heartbeat interval, assert an old attempt cannot complete it after a replacement claim, and force a retry through `AGENT_PROCESSING_MAX_ATTEMPTS` until one `event_processing_dlq` row exists. Unit tests validate control flow but do not type-check SQL against PostgreSQL.

For a full queue-drain proof, run the load on dedicated PGMQ queues, then use `powershell -File apps/agent/tests/load/verify-queue-drain.ps1 -Queue <result-queue> -ExpectedCount <N> -Drain`. It requires exactly `N` distinct transaction keys, deletes through `pgmq.delete`, and fails unless the queue reaches zero. Verify the dedicated request queue with `-ExpectedCount 0` as well. Never point this cleanup helper at a shared or production queue.
