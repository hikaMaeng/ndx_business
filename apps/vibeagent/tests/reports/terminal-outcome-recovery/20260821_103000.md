# Duplicate transaction terminal-outcome report

## Revision

- `84bee66 fix(agent): join duplicate transaction jobs`
- Deployed through `npm run deploy agent`; the `agent` container was `running/healthy`.

## Live PostgreSQL scenario

1. Submitted `test.delay` with `simulateDelayMs=20000`.
2. Submitted the same command with the same `transactionKey` two seconds later.
3. Waited until the original execution completed, then inspected the event store, execution, processing jobs, DLQ, result queue, and metrics.

The delay exceeds the previous five-attempt retry budget (about 15 seconds), so this is the collision that formerly allowed a duplicate job to create a false permanent-failure result before the actual success.

| Check | Observed value |
| --- | --- |
| Command events | 2 |
| Terminal result events | 1 |
| Terminal result | `result`, `ok=true` |
| Execution | `completed`, `ok=true` |
| Processing jobs | 2 `completed`, one attempt each |
| DLQ rows for transaction | 0 |
| `processingJoined` metric delta | 1 |
| `processingRetries` / `processingDlqTotal` delta | 0 / 0 |

The duplicate was joined to the in-progress transaction; it neither retried nor occupied the transaction result identity.  The test's exact result-queue messages and database rows were removed afterward without draining shared queues.
