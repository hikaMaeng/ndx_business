# 이벤트 정체성과 멱등성 — 실행 보고

- 계기: "pgmq의 메세지 확보는 재요청·타임아웃 리트라이를 막아주지 않는다"
- 실행: 2026-08-27 14:20 ~ 15:15 (KST)
- 결과: 지적이 맞았다. **기존 멱등성은 우연에 기대고 있었다.** 세 층으로 나눠 고쳤다

## 먼저 확인한 것 — 무엇이 이미 있었나

브로커 차원의 멱등 장치는 실재했다.

| 장치 | 키 | 동작 |
| --- | --- | --- |
| `agent_execution` | `transaction_key` | claim이 `ON CONFLICT DO NOTHING`. 리스가 살아 있는 동안의 재전달은 `joined` 로 돌아가 **실행되지 않는다** |
| `event_store` | `event_id` | `ON CONFLICT (event_id) DO NOTHING` |

리스를 잃으면 실제로 작업이 죽는 것도 확인했다 — `renew` 실패 시
`controller.abort()` 가 `runBash` 의 signal까지 전달되어 자식 프로세스가 종료된다.
"좀비가 계속 파일을 쓴다" 는 아니다.

## 진짜 결함 — 키가 내용이 아니라 위치였다

```ts
eventId: deterministicEventId(`progress:${transactionKey}:${streamId}:${seq}`)
//                                                                    ↑ 실행 내 발급 순번
```

`seq` 가 **그 실행에서 몇 번째로 발급했는가**다. 스트리밍 반응기가 재실행되면
모델이 델타를 다른 개수·다른 내용으로 뱉으므로, 같은 순번에 다른 내용이 붙는다.
`DO NOTHING` 이 먼저 것을 남기고 뒤엣것을 버리므로 **두 실행이 섞인 전사**가 되고,
재실행이 더 많이 발급하면 꼬리는 그대로 추가된다.

즉 지금까지의 중복 제거는 순번이 우연히 맞아떨어져서 성립했다. 보장이 아니었다.

## 고친 방식 — 층마다 다른 답

### 1. 델타는 펜싱

멱등하게 만들 수 없다. 재실행의 델타는 중복이 아니라 **다른 답**이다. 그래서
리스를 잃은 attempt는 발급 경로 진입점에서 즉시 멈춘다.

```ts
if (leaseLost) return;
```

인메모리 불리언이라 비용이 없고, 이전에는 abort가 다음 await까지 도달할 때까지
계속 썼다.

### 2. 결정적 사실은 생성자 발급 논리키

발급자가 그 사실이 무엇인지 말한다. 브로커는 `key` 가 있으면
`deterministicEventId("fact:<streamId>:<key>")` 를 쓴다.

**실제로 동작하는지 독립 계산으로 확인했다.** 저장된 event_id를 꺼내
같은 유도식을 밖에서 다시 계산했다.

```
model.replied:405052ce-88c1-4c8a-9dd1-adb1786164dc:0
  stored  94e685bc-d230-833b-9864-949e25f01683
  derived 94e685bc-d230-833b-9864-949e25f01683   MATCH
model.replied:405052ce-88c1-4c8a-9dd1-adb1786164dc:1
  stored  7b2dfce5-94b5-8db7-9d77-56299170860c
  derived 7b2dfce5-94b5-8db7-9d77-56299170860c   MATCH
```

컴파일만 된 게 아니라 살아 있다. 반응기가 통째로 다시 돌아도 같은 사실은 한 행이다.

### 3. 명령은 실행 전에 확인

키로 접을 수 없는 유일한 것. spawn 전에 히스토리에 "이 호출에 이미 답이 있는가"를
묻고, 있으면 기록된 결과로 사실만 다시 남긴다. 완료 직후 재전달이라는 가장 흔한
경우가 사라진다.

## 검증

병렬 도구 호출 세션을 새로 돌렸다. 팬아웃 수가 정확히 맞는다.

```
turn.started     progress 1 / command 2   (model, view)
model.replied    progress 3 / command 6   (decide, view)
tool.requested   progress 4 / command 4   (tool)
tool.completed   progress 4 / command 8   (join, view)
iteration.ready  progress 2 / command 2   (model)
turn.final       progress 1 / command 1   (view)
```

산출물 `a.txt b.txt c.txt` 생성 확인.

단위 테스트 4개를 추가했고(총 42개), **가드를 제거하면 실제로 실패하는지** 확인했다.

```
✖ a command that already has a recorded answer is not run again
✖ the replayed completion carries the exit code that actually happened
✖ the completion keeps its identity when replayed, so it collapses with the original
```

복원 후 42/42 통과.

## 권고했으나 하지 않은 것

**별도의 "처리된 UUID" 테이블은 만들지 않았다.** `event_store(event_id)` 와
`agent_execution(transaction_key)` 가 이미 그 테이블이다. 세 번째를 만들면 앞의
둘과 일관성을 맞춰야 할 대상이 하나 늘 뿐이고, 어느 것이 진실인지 물을 자리가
생긴다.

## 남은 창

리스 만료로 다른 워커가 재클레임하는 순간과, 원래 워커가 다음 heartbeat에서 그걸
알아채는 순간 사이에 두 실행이 겹칠 수 있다. 현재 heartbeat 주기는
visibility/3 = 20초, 도구 타임아웃은 120초다.

완전히 닫으려면 **펜싱 토큰**이 필요하다. `agent_execution.attempts` 가 이미 단조
증가하니 토큰은 공짜이고, 도메인 쓰기까지 관통시켜 낡은 attempt의 쓰기를 거부하면
된다. 쓰기마다 검사가 붙는 침습성 때문에 지금은 권고로 남긴다.
