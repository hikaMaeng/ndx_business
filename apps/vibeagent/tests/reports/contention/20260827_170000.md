## 먼저: 내가 틀렸던 것

여러 커밋과 보고서에서 "디스패처 재시작을 건넌 fact는 유실된다"고 적었다.
**사실이 아니다.**

커서는 `event_reader_cursor` 의 행이다. 재시작해도 남아 있고, 디스패처는 멈춘
자리에서 이어간다. 첫 카오스 시도에서 그게 드러났다 — 디스패처를 죽이고 턴을
넣은 뒤 다시 띄웠더니, 청소 루프가 아니라 **평범한 드레인 경로가** 그 턴을
처리했다. 회수 로그가 한 줄도 안 찍혔다.

```
docker logs …dispatcher | grep recovered   →   (없음)
```

진짜 구멍은 훨씬 좁다: **저장된 커서가 없는** 디스패처. 로그 끝에서 시작하므로
그 앞을 전부 건너뛴다. 첫 기동, 이름 변경, 커서 행 유실.

그래서 시나리오를 고쳐 그 상태를 일부러 만들었다 — 커서 행을 지우고 띄웠다.
그제야 진짜가 나왔다.

```
{"event":"broker.fact.dispatch.seeded","dispatcher":"vibe","streams":41}
{"event":"broker.fact.dispatch.recovered","dispatcher":"vibe","resent":2,"examined":399}
```

399건을 살펴 2건만 다시 보냈다. 정확하다.

## 넣은 것 — 나이로 찾는 청소 루프

위치로는 못 찾는다. **위치가 실패한 바로 그것**이기 때문이다. 나이로 찾는다:
반응이 진작 끝났어야 할 만큼 오래된 fact인데 그에 해당하는 실행 기록이 없으면
누락이다.

도메인을 모른다. "반응표에 있는 action" 과 "정착된 실행" 만 알면 되고, 턴이
무엇인지는 알 필요가 없다.

다시 보내는 것은 어느 경우에도 안전하다 — 도는 반응은 클레임이 흡수하고, 끝난
반응은 기록된 결과로 건너뛴다. 유예 시간은 정확성이 아니라 낭비를 줄이는 값이다.

계정 간 가시성도 통과했다 — 각 계정이 자기 세션만 보고, 남의 세션 전사 요청은
404다.

카오스 프롬프트는 `>>` 로 덧붙인다. 명령이 두 번 돌면 내용이 두 배가 된다.

```

chaos-mtb4txv3/s0/s0.log: [s0]
```

전부 한 번씩. **워커를 턴 중간에 죽였는데도** 명령이 두 번 돌지 않았다. 펜스와
"이미 답이 있는가" 가드가 버텼다.

## 고친 낡은 스크립트

`vibe-turn-e2e.mjs` 와 `vibe-concurrent-sessions.mjs` 는 **둘 다 이미 깨져 있었다.**
세션을 열지 않고 `turn.run` 을 보내서, 프로젝트가 폴더를 갖게 된 뒤로는 거부된다.

고치면서 같은 결함이 둘 다에 있는 것도 발견했다.

```js
if (kind === "result" || kind === "failure") { /* 끝났다고 판단 */ }
```

반응기 구조에서 `result` 는 **한 반응의** 종료이지 턴의 종료가 아니다. 턴은 이제
반응의 사슬이고, 가장 먼저 오는 result는 **세션 개설**이다. 그래서 두 스크립트 다
300ms 만에 "완료" 로 끝나고 있었다 — `vibe-concurrent-sessions.mjs` 는 그 때문에
"직렬 실행으로 보인다" 며 실패했다. 정직한 실패였지만 이유가 틀렸다.

`turn.final` 을 기다리도록 고쳤다. 고친 뒤:

```
sessions 4, peakInFlight 4, wall 21.7s, serialWouldBe 85s
```

`vibe-turn-e2e.mjs` 의 `workspaceUrl` 이 세션 id를 가리키던 것도 고쳤다 —
폴더는 이제 프로젝트의 것이다.
