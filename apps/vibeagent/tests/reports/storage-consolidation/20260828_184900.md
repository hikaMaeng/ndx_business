## The defect this surfaced

`docker inspect admin` showed `/var/lib/postgresql` bound to
`b1b5caff…` — an **anonymous** volume, created because the base postgres image
declares `VOLUME /var/lib/postgresql`. It appeared in no compose file. It held
116 sessions and 66,183 facts.

It survived the `docker compose down` performed here only because `-v` was not
passed; the following `up` would have attached a fresh empty volume in its
place, with no error and no warning. It is now a declared bind mount.

## Residual risk

- **First start on a fresh data root is slower.** initdb writes ~1,500 files
  across the Windows host bridge. Measured once at roughly a minute; not on any
  hot path, but a cold clone will feel it.
- **Sustained Postgres throughput on a bind mount was not measured.** Correctness
  and durability were. If the fact log gets write-heavy this is the first thing
  to benchmark.
- **The mask is per-service.** A new container that mounts the projects root and
  forgets the tmpfs line gets unguarded access to the database files. It is a
  convention held by three copies in `docker-compose.yml`, not by a mechanism.
- **Two stale artefacts were left in place, deliberately, as they are data:**
  `.ndx/admin/data/admin.sqlite` (257 MB, an older path superseded by
  `admin/admin.sqlite`) and the orphaned `ndx-business_vibeagent_workspace`
  volume (88 KB of pre-bind-mount session folders). Neither is read. Removing
  them is a decision for the owner, not a side effect of this change.
- The three source volumes still exist and still hold the pre-migration copies.
