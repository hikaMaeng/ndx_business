## 연쇄가 돌았다는 증거

`calc-events` 의 이벤트를 action·kind·audience 로 집계했다. 연쇄는 이 표에서 읽힌다.

```
vibe.turn.run          command  client    4      ← 클라이언트가 시킨 것
vibe.turn.started      progress client    4      ← 반응기가 남긴 사실
vibe.turn.started      command  worker    4      ← 디스패처가 model 큐로
vibe.model.replied     progress worker   11
vibe.model.replied     command  worker   10      ← decide 큐로
vibe.tool.requested    progress worker    7
vibe.tool.requested    command  worker    7      ← tool 큐로
vibe.tool.completed    progress client    7
vibe.tool.completed    command  worker    7      ← join 큐로
vibe.iteration.ready   progress worker    7
vibe.iteration.ready   command  worker    7      ← 다시 model 큐로
vibe.turn.final        progress client    3
```

`progress` 는 반응기가 남긴 사실이고, 같은 action의 `command` 는 디스패처가 반응표를
보고 큐에 넣은 사본이다. 두 줄이 짝을 이룬다는 것이 곧 "사실 → 반응표 → 반응기" 가
돌았다는 뜻이다. 어느 반응기도 다음 반응기를 부르지 않았다.

`model.replied` 만 11:10 으로 하나 어긋난다. 마지막 것은 `turn.final` 로 끝난
답변이라 decide 뒤에 이어질 반응이 없다. 정상이다.

audience 분리도 지켜졌다.

```
client  progress 1856   client  result 131   client  command 13
worker  command   119   worker  progress 86
```

워커끼리 오간 86 + 119 건은 클라이언트 채널 읽기(`audience <> 'worker'`)에
한 건도 섞이지 않았다.

**폭주 없음**: `iteration.started` 가 세션별 10·9·14 로, 실제 도구 호출 횟수와 맞는다.
계획이 정한 중단선(15)을 넘지 않았다.

## 발견하고 고친 결함

1. **`1.5+2.5` 가 26.5** — 생성된 코드가 소수점 검사에서 연산자 **id 문자열**
   (`"btn-plus"`)을 표시 텍스트에서 찾았다. 절대 못 찾으니 현재 피연산자가 늘 수식
   전체였고, 이미 `.` 이 있으니 두 번째 소수점이 조용히 버려졌다 → `1.5+25`.
   두 턴을 추측으로 낭비한 뒤 코드를 직접 읽어 원인을 짚어주자 고쳐졌다.
   **교훈**: 에이전트에게 증상만 주면 겉을 고친다. 원인을 주면 원인을 고친다.

2. **디스패처가 과거를 재생** — 저장된 커서가 없을 때 0에서 시작해 이미 끝난 턴을
   전부 새 일감으로 뿌렸다. 커서가 없으면 로그 끝에서 시작하도록 고쳤다.

3. **반응 사본이 사실의 transactionKey 를 재사용** — 이미 끝난 작업으로 보여 클레임이
   거부했다. 반응마다 `react:<queue>:<factEventId>` 로 고유 키를 만들도록 고쳤다.

## 남은 위험

**디스패처 재시작 중 비행 중이던 사실은 유실된다.** 실제로 관측했다. 세션
`…2d3b2fe0` 은 `model.replied` 까지 남기고 멈춰 있다 — 그 사실이 20:14 에 기록됐고
현재 디스패처는 20:24 에 떴다. 커서가 없으면 로그 끝에서 시작하니 그 앞의 사실은
영원히 읽히지 않는다.

이건 결함 2의 고의적인 대가다. 과거를 재생하지 않으려면 과거를 버려야 한다. 다만
"이미 끝난 턴"과 "끝내지 못한 턴"을 지금은 구분하지 못한다. 재시작이 잦은 운영에서는
미완결 턴을 찾아 되살리는 장치가 따로 필요하다. 이번 검증 범위 밖으로 둔다.

부차적으로, 세션 `…2d3b2fe0` 처럼 죽은 세션이 좌측 목록에 계속 남는다. 정리 수단이 없다.
