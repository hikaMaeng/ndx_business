## 리뷰 지적별 확인 결과

### 1. 조인 경합 — 사실. 가장 심각. 수정함

`joinTools` 가 카운트만 보고 발급했다. 도구 호출 N개면 반응기가 N번 깨어나고,
마지막 둘은 두 쓰기가 모두 커밋된 뒤에 읽을 수 있어 **둘 다 N of N** 을 본다.
둘 다 옳다. 직렬화해도 마찬가지다 — 누가 마지막에 읽었는지가 아니라 누가 말할
권리를 갖는지의 문제이고, 그건 유일성이다.

리뷰의 가장 아픈 지적도 사실이었다. 로그 전체를 세어 확인했다.

```
calls | iterations
    1 |         39
```

**39이터레이션 전부 도구 호출 1개.** N≥2 가 한 번도 실행된 적이 없다. 자랑하던
경로가 곧 테스트 안 된 경로였다는 지적 그대로다.

`vibe_iteration_ready` 래치를 넣고 `ON CONFLICT DO NOTHING` 이 행을 반환한
반응기만 발급하게 했다. 실제 Postgres에서 동시 삽입을 확인했다.

```
first_won | second_won
        1 |          0
```

**그리고 실제로 N≥2 를 처음 돌렸다.** 모델에게 한 메시지에 도구 호출 3개를
담게 했다.

```
tool.requested progress 3      ← 병렬 3개
tool.completed progress 3
iteration.ready progress 1     ← 조인 3번, 발급 1번
turn.final      progress 1
vibe_iteration_ready: (turn cb4ac8c8, iteration 0) 한 행
```

히스토리도 깨끗하다. 이터레이션 0에 assistant 1 · tool 3 · user 1, 이터레이션 1에
assistant 1. 대화가 갈라지지 않았다.

### 2. 반응기 재시도가 멱등이 아님 — 사실. 수정함

재시도 표면을 코드로 확인했다. 평범한 throw는 `worker_failed` 로 종결되고,
`WorkerLostError` 만 최대 5회 재시도된다. 그것이 정확히 "절반 실행된 반응기가
다시 도는" 경우다 — `callModel` 은 assistant 메시지를 쓴 **뒤** 사실을 발급한다.

`vibe_session_message` 에 자연키 유니크 인덱스를 걸고 append를 `ON CONFLICT DO
NOTHING` 으로 바꿨다. 기존 데이터에 위반이 없음을 먼저 확인했다(중복 0건).

```
INSERT assistant 'first'            → INSERT 0 1
INSERT assistant 'retry duplicate'  → INSERT 0 0
남은 것: 1행, content = 'first'
```

덮어쓰지 않는 이유는 먼저 쓰인 것이 이미 하류가 반응한 버전이기 때문이다.

### 3. 시퀀스 블록 절벽 — 사실. 수정함

8192번째에서 throw했다. 관측된 최대가 이터레이션당 델타 1084개로 여유 7배지만,
터지는 자리가 최악이다 — 인퍼런스 비용을 다 치른 뒤 스트림 중간이다.

절반 지점에서 다음 블록을 미리 받아오게 했다. 새 블록은 항상 이전 블록 끝보다
뒤에서 시작하므로 위치는 계속 증가한다. 남은 위치를 버리는 건 상관없다 — 위치는
비교하는 것이지 세는 것이 아니다. 리필이 4096번의 발급과의 경합에서 지면 여전히
throw하지만, 그건 들을 만한 사건이다.

### 4. 디스패처 단일점 — **부분적으로 반박**

리스가 없는 것은 사실이고, HA 구성이 없는 것도 사실이다. 그러나 "둘 띄우면
유실이 생긴다"는 성립하지 않는다. 리뷰 본인이 문장 중간에 반쯤 철회한 대로,
디스패치 사본의 정체성이 결정적이기 때문이다.

```ts
const identity = deterministicEventId(`react:${queueName}:${fact.eventId}`);
```

같은 사실 + 같은 큐 = 같은 id = 같은 transactionKey. 두 디스패처가 같은 범위를
읽으면 **같은 사본**을 만들고 반응기 클레임이 흡수한다. 커서는 어느 쪽이 저장해도
"누군가 실제로 보낸 지점"만 담으므로 건너뛰지 않는다. 낮은 값이 저장되면 재발송이
일어나고 그것도 흡수된다.

즉 둘 이상은 **낭비지 유실이 아니다**. 리스는 최적화이지 정합성 수정이 아니므로
지금 넣지 않았다.

진짜 남은 구멍은 그 옆에 있다. **디스패처 재시작을 건너는 사실은 유실된다** —
커서가 없으면 로그 끝에서 시작하기 때문이고, 끝난 턴과 못 끝낸 턴을 구분하지
못한다. 읽기 쪽은 뷰 리빌드로 완화했지만 **기계는 여전히 멈춘다**. 미완결 턴을
찾아 되살리는 장치가 따로 필요하다.

### 5. 반응기 계층 테스트 0 — 사실. 보완함

`server` 아래 테스트가 `config` 와 `bash` 둘뿐이었다. 조인과 판정에 단위 테스트
11개를 넣었다.

**회귀 테스트가 실제로 잡는지 확인했다.** 클레임을 임시로 제거하고 돌렸다.

```
✖ two reactors that both see every call answered declare it ready once
✖ a redelivered tool.completed cannot declare the same iteration ready twice
```

복원 후 38/38 통과. 실패한 적 없는 회귀 테스트는 아무것도 증명하지 않으므로
이 확인을 거쳤다.

판정 쪽 테스트가 덮는 것: 도구 없는 응답이 턴을 끝내는가, N개 호출이 N개 사실로
갈라지는가, `toolCallKey` 가 위치에서 유도되는가, 이터레이션 예산이 호출 대신
종료를 내는가, 파싱 불가능한 인자도 사실을 내서 조인이 영원히 기다리지 않는가,
assistant 메시지가 없을 때 침묵이 아니라 답으로 처리하는가.

## 총평에 대하여

리뷰의 진단이 정확했다. "인과 사슬은 완벽한데 팬인의 멱등성이 비어 있다" 는 것이
결함 1·2의 공통 뿌리이고, 제어를 없앤 대가가 정확히 거기서 청구된다.

문서에도 반영했다 — `packages/vibeagent_domain/docs/constraints.md` 의
"팬인은 멱등해야 한다".

## 부수적으로 고친 것

같은 문서에 사실과 다른 서술 두 곳이 있었다. workspace를 `<root>/<sessionId>` 로
적고 "세션은 다른 세션의 파일에 닿을 수 없다" 고 했는데, 프로젝트가 폴더를 갖게
된 뒤로 **같은 프로젝트의 여러 세션은 같은 폴더를 공유한다**. 격리 경계는 세션이
아니라 프로젝트다. 의도된 동작이므로 서술을 사실에 맞췄다.

## 남은 것 (우선순위 순)

1. **미완결 턴 되살리기** — 디스패처 재시작을 건넌 턴은 지금도 멈춘 채 남는다
2. 디스패처 리스 — 정합성이 아니라 중복 작업 절감
3. `callModel` / `runTool` / `openTurn` 단위 테스트 — 이번엔 조인과 판정만 덮었다
4. 대량 백필 명령
