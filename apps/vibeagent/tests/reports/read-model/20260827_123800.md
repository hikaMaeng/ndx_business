### 6. 라이브 접기와 수치

턴 2를 제출하자 턴 1이 그 자리에서 접혔다. 되연 세션이 아니므로 이 수치는 읽기
모델이 아니라 라이브 리듀서가 낸 것이다: `이터레이션 3 · 도구 2`.

그 상태에서 접힌 턴을 펼치자 뷰에서 6블록이 돌아왔다 — 본문이 메모리에서
버려졌다가 되돌아온 왕복이 확인됐다.

### 7. 자동 스크롤

스트리밍이 도는 동안 700ms마다 바닥과의 간격을 쟀다.

```
samples: 62, atBottom(≤80px): 62, strayed: []
```

한 번도 이탈하지 않았다. 같은 샘플에서 `folded: 1` 이 내내 유지돼, 접기가
스트리밍 중에도 안정적이라는 것도 함께 보였다.

### 8. 블록 순서

7이터레이션 턴을 되불러와 블록 종류를 순서대로 읽었다.

```
reasoning → tool:{ printf '\n## Thi → reasoning → tool:ls -l → reasoning →
message → tool:{ printf … → reasoning → tool:{ printf … → reasoning →
tool:cat notes.md → reasoning → message → tool:cat > notes.md → reasoning → message
```

생각하고 실행하고 다시 생각하는 순서가 그대로 살아 있다.

## 발견하고 고친 결함

1. **`ORDER BY seq` 가 문자열 정렬이었다** — 가장 나쁜 종류의 결함.
   `SELECT seq::text … ORDER BY seq` 에서 PostgreSQL은 ORDER BY를 **출력 컬럼**에
   먼저 맞춘다. `seq::text` 의 라벨이 `seq` 라서, 정렬이 캐스팅된 문자열로 일어났다.
   `"1" < "180225" < "90113"` → 대화가 1, 3, 2 순으로 표시됐다.
   턴 목록과 블록 목록 **양쪽 모두** 같은 버그였고, 블록 쪽은 한 턴 안의
   추론·도구 순서를 뒤섞었을 것이다.
   `seq::text AS seq_text` 로 고쳤다.

   실측이 아니었으면 놓쳤다. 앞선 두 세션은 seq가 우연히 사전순과 숫자순이
   같아서 정상으로 보였다.

2. **보이는데 안 불러오는 턴** — 되연 세션의 최근 턴은 `showing` 이지만 본문이
   없다. 그런데 `expandTurn` 은 클릭에서만 불렸다. "과정을 불러오는 중…" 에서
   영원히 멈춘다. 페인트마다 "보이면 적재, 안 보이면 해제"를 맞추도록 고쳤고,
   요청 중복을 막는 in-flight 집합을 클라이언트에 뒀다.

3. **라이브로 접힌 턴에 수치가 없었다** — 수치는 읽기 모델에서만 왔는데, 보고
   있는 동안 접힌 턴은 읽기 모델을 거치지 않는다. 같은 집계를
   `iteration.started` / `tool.started` 리듀서에도 넣었다.

  지금까지는 그것으로 충분했다
