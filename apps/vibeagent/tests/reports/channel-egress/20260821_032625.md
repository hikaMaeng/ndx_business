# Cursor delivery and replay verification

## Environment

- Deployed target: `http://127.0.0.1:18081` / `ws://127.0.0.1:18081/ws`
- Database: deployed `admin` PostgreSQL container
- Isolation prefix: `cursor-ack-1787250360755`

## Executed steps

1. Subscribe to `agent.results` without a cursor and submit one `hash.sha256` command.
2. Wait for its terminal result, close the socket, reconnect with the returned opaque cursor, and submit a second command on the same stream.
3. Query the durable cursor and event stream positions, inspect the actual replay query plan, then delete only rows and PGMQ messages bearing the isolation prefix.

## Results

| Check | Result |
| --- | --- |
| First terminal result | `1` |
| First result replayed after reconnect | `0` |
| Second terminal result | `1` |
| Cursor position / stored stream high-water | `4 / 4` |
| Replay plan | nested-loop index scan using `event_store_channel_stream_sequence_idx`; `0.485 ms` on the live dataset |
| Cleanup residual (`event_store|execution|cursor|PGMQ`) | `0|0|0|0` |

## Invariants covered

- Cursor advances only after the WebSocket send callback completes; a reconnect did not replay an acknowledged event.
- Replay is bounded by per-stream high-water and position in PostgreSQL rather than materializing complete channel history in the Agent process.
- UUID cursor state is durable and receives a seven-day retention bound through `AGENT_CURSOR_RETENTION_DAYS`.
