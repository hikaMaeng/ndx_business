# 읽기 모델과 전사 접기 — 검증 계획

## 목표

세션을 다시 여는 비용을 로그 리플레이에서 떼어내고, 화면에 남는 것을 보고 있는
것으로 한정한다.

세 가지가 참이어야 한다.

1. 뷰 워커가 **다른 워커를 모른 채** 같은 사실에 반응해서 전사를 접어 저장한다
2. 접힌 턴은 본문을 메모리에서 버리고, 펼치면 한 번의 요청으로 되불러온다
3. 프로젝션 테이블은 버려도 되는 것이어야 한다 — 로그가 다시 만든다

## 환경

- 컨테이너: `admin`, `vibeagent`, `vibeagent-worker`, `vibeagent-dispatcher`
- 큐 여섯: `vibe_intake`, `vibe_model`, `vibe_decide`, `vibe_tool`, `vibe_join`, **`vibe_view`**
- 클라이언트 `http://localhost:18081`, 크롬 확장으로 조작
- 프로젝트 `view-fold` (신규)

## 사전 조건

1. `npm run lint`, `npm test` 통과
2. 워커 기동 로그의 `queues` 에 `vibe_view` 가 있을 것
3. 디스패처 기동 로그의 `actions` 에 `vibe.turn.final` 이 있을 것 — 뷰만 반응하는 사실이다
4. `vibe_turn_view`, `vibe_block_view` 두 테이블이 생성되어 있을 것

## 단계

1. **콜드 리빌드** — 프로젝션보다 오래된 세션을 연다. 리플레이 없이 복원되어야 한다.
   접힌 턴에 수치가, 최근 턴에 본문이 보여야 한다
2. **펼치기** — 접힌 턴의 토글을 누른다. 블록 수가 늘고 도구 명령이 실제 명령이어야 한다
3. **접기** — 다시 누른다. 블록 수가 줄되 **답변은 남아야** 한다
4. **라이브 프로젝션** — 새 프로젝트에 세션을 열고 턴을 돌린다. DB에 뷰 행이 쌓이는지 본다
5. **접기 비율** — 델타 이벤트 수와 블록 행 수를 센다. 이것이 프로젝션의 존재 이유다
6. **라이브 접기** — 두 번째 턴을 돌린다. 첫 턴이 그 자리에서 접히고 **수치가 보여야** 한다.
   되연 세션이 아니므로 이 수치는 읽기 모델이 아니라 라이브 리듀서가 낸 것이다
7. **자동 스크롤** — 스트리밍 내내 바닥과의 간격을 샘플링한다. 80px 이내를 유지해야 한다
8. **라이브 접힌 턴 되불러오기** — 6에서 접힌(본문이 버려진) 턴을 펼친다.
   뷰에서 되불러와 라이브와 같은 내용이 나와야 한다

## 기대 결과

- 델타 수백 건 → 블록 한 자리 수
- `iterations` / `tool_calls` 가 실제 수와 일치 (재전달로 부풀지 않음)
- 접기·펼치기가 블록 수를 오르내리게 하되 답변은 불변
- 스트리밍 중 바닥 이탈 0회
- 되불러온 본문에 마크다운 렌더러가 적용될 것 — 라이브와 구분되지 않아야 한다
