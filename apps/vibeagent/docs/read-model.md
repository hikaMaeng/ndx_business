# 읽기 모델

## 왜 필요했나

이벤트 로그는 진실이지만, 세션을 화면에 되살리는 용도로는 최악이다.

한 턴의 한 이터레이션이 리즈닝 델타 1084건이다. 끝난 세션을 다시 열 때
채널을 처음부터 리플레이한다는 것은, 브라우저가 받자마자 문단 하나로 합쳐버릴
이벤트 수만 건을 그대로 실어 보낸다는 뜻이다. 접는 결과는 매번 똑같다.

똑같은 접기라면 한 번만, 들어올 때 하면 된다.

## 무엇이 하나

`vibe_view` 큐를 감시하는 워커가 다른 워커들과 **같은 사실에 반응해서** 두 테이블을 쓴다.

| 테이블 | 담는 것 |
| --- | --- |
| `vibe_turn_view` | 접힌 턴이 보여줄 것 — 질문, 국면, 답변, 이터레이션·도구 수 |
| `vibe_block_view` | 펼친 턴이 보여줄 것 — 접힌 리즈닝·답변·도구 출력 본문 |

둘 다 진실의 원천이 아니다. 지워도 로그가 다시 만든다. 그게 말뿐이 아니라는
증거가 `ViewStore.rebuild()`이고, 읽기 경로가 비어 있는 세션을 만나면 그걸 부른다.

## 어떻게 붙었나

반응표에 팬아웃 항목을 더한 것이 전부다.

```ts
[VIBE_ACTIONS.turnStarted]:   [QUEUES.model,  QUEUES.view],
[VIBE_ACTIONS.modelReplied]:  [QUEUES.decide, QUEUES.view],
[VIBE_ACTIONS.toolCompleted]: [QUEUES.join,   QUEUES.view],
[VIBE_ACTIONS.turnFinal]:     [QUEUES.view],
```

같은 사실을 두 큐가 **각자의 사본으로** 받는다. 경합 소비가 아니라 팬아웃이라,
뷰 워커는 모델 워커를 모르고 모델 워커는 뷰 워커의 존재조차 모른다. 위 네 줄을
지우면 읽기 모델이 사라지고 기계는 그대로 돈다.

프로젝션을 사실을 만드는 리액터 안에 넣지 않은 이유가 여기 있다. 접기는 느린
일이고(델타 천 건을 되읽는다), 그걸 추론 경로에 두면 사용자에게 답하는 일이
아무도 아직 안 보는 기록 작업을 기다리게 된다.

## 큐가 곧 주소

`model.replied`는 한 큐에서 "판단하라"이고 다른 큐에서 "기록하라"다. 액션만으로는
구분되지 않고 엔벨롭도 구분해주지 못한다 — 같은 사실이니까. 다른 것은 **누구에게
보낸 사본인가**뿐이고, 그건 큐 이름이 말해준다.

그래서 워커는 `(큐, 액션)` 쌍으로 라우팅한다.

```ts
worker(event, queue) {
  reactors[queue][event.action](globals, session, event, emit)
}
```

## 세션 핸들은 요청해야 온다

세션 핸들을 받으면 세션 행에서 시퀀스 블록을 떼어간다. 아무것도 발행하지 않는
뷰 리액터가 이벤트마다 블록을 낭비하고 뜨거운 행에 경합할 이유가 없다.

그래서 핸들은 지연 로딩이고, **요청하는 행위 자체가 "나는 발행할 것이다"라는
선언**이다. 뷰 리액터는 한 번도 요청하지 않는다.

## 멱등성

프로젝션은 at-least-once 큐가 먹인다. 같은 사실이 두 번 와도 같은 행이 나와야지,
행이 둘이 되거나 본문이 두 배가 되면 안 된다. 그래서 이 안에는 append가 없다.

* 모든 쓰기가 사실이 지목하는 것을 키로 하는 upsert
* 이터레이션 수는 `greatest(iterations, index + 1)` — `+ 1`이 아니다
* 도구 수는 블록 테이블에 되물어 계산 — 증가시키지 않는다

## 클라이언트가 쓰는 방식

세션을 다시 열면 리플레이 대신 이 두 경로를 쓴다.

| 경로 | 답하는 것 |
| --- | --- |
| `GET /api/vibe/sessions/:sessionKey/turns` | 턴 목록. 본문 없음 |
| `GET /api/vibe/sessions/:sessionKey/turns/:turnKey` | 그 턴 하나의 본문 |

소유권은 브로커가 리플레이에 쓰는 것과 같은 접두사 규칙이다. 세션 id가 소유자
id로 시작하므로 조회 없이 답한다.

화면 규칙은 하나다. **보이는 것은 적재되어 있고, 안 보이는 것은 해제된다.**

* 실행 중인 턴과 가장 최근 턴은 항상 보인다
* 그 외 끝난 턴은 접히고 본문이 메모리에서 버려진다
* 펼치면 그 턴만 한 번의 요청으로 되불러온다
* 답변은 접혀도 남는다. 되돌아 읽는 사람이 원하는 건 결론이고, 과정은 요청하면 된다

되불러온 본문은 라이브 본문과 **같은 `TurnBlock` 경로**를 탄다. 그래서 마크다운
렌더러가 자동으로 적용되고, 방금 본 턴과 한 시간 뒤 되연 턴이 구분되지 않는다.

## 접힌 턴의 수치는 두 곳에서 온다

되연 세션의 턴은 읽기 모델이 수치를 준다. 하지만 **보고 있는 동안 접힌 턴**은
읽기 모델을 거치지 않는다 — 다음 턴이 시작되면 그 자리에서 접힌다.

그래서 같은 집계를 라이브 리듀서도 한다. `iteration.started`가 이터레이션을,
`tool.started`가 도구를 센다. 둘 다 재전달에 부풀지 않도록 `max`와 재계산을 쓴다.

## 프레임당 한 번만 그린다

턴 하나가 이벤트 수천 건으로 도착하고 모델은 그때마다 commit한다. 매번 그리면
아무도 그 속도로 읽을 수 없는 텍스트를 위해 초당 수천 번 문서를 재구성하고
마크다운을 다시 파싱하고 새니타이저를 다시 돌린다.

이벤트 스트림만 `requestAnimationFrame`으로 합친다. 클릭과 키 입력은 즉시 그린다 —
스트림에 늦게 반응하는 것과 사람에게 늦게 반응하는 것은 다른 일이다.

## 자동 스크롤

바닥을 따라가되, 위를 읽고 있으면 건드리지 않는다.

`innerHTML`을 갈아끼우면 스크롤이 0으로 돌아가고 "바닥에 있었나"라는 질문의 답이
사라지므로, 교체 **전에** 측정한다. 그리고 하이드레이션 **후에** 적용한다 —
방금 그려진 다이어그램이 높이에 포함되어야 한다.

## 아직 없는 것

리빌드는 요청이 올 때 세션 단위로 일어난다. 대량 백필 명령은 없다. 세션은
누군가 열 때 스스로 채워지므로 지금까지는 필요하지 않았다.
