# Admin render loops and the strays they left — execution report

- **When**: 2026-08-28 19:40 KST
- **Against**: the deployed stack, `http://localhost:18080`
- **Verdict**: **PASS, after fixing two defects found during the run.**

## The defect that mattered

`/api/auth/me` was being called **186 times in 5 seconds** — roughly 37 per
second, continuously, for as long as an admin page stayed open. Nothing on
screen looked wrong, and the console showed one incidental error.

`AdminShell` listed two unstable values as effect dependencies:

```tsx
const text = texts(language);              // fresh object every render
<AdminShell onLogout={() => {...}} />      // fresh function every render
useEffect(() => { ...setCurrentUser(user) }, [onLogout, text, token]);
```

The effect sets state, the render rebuilds both dependencies, the effect runs
again. This is the same fault fixed earlier in the models screen; fixing it
there and not sweeping for siblings is why it survived.

| | before | after |
| --- | --- | --- |
| `/api/auth/me` in an 8s window | ~300 | **1** |

`AccountScreen` carried the same dependency. Its `status !== "idle"` guard
keeps the happy path from spinning, but its failure branch resets the status to
`idle`, so one failed load became a retry storm. Fixed the same way.

## The stray databases

Two silent defaults opened a database when nobody named one:

| Site | Effect |
| --- | --- |
| `env.ts` `AUTH_DATABASE_PATH ?? "./data/admin.sqlite"` | an unset variable starts the service against an empty store, with no error |
| `app.ts` same default inline | two tests called `createApp()` with no database, so running the suite wrote `apps/admin/data/admin.sqlite` into the repository |

Both now require an explicit path — `env.ts` throws like `PORT` and `NODE_ENV`
already did. The two health tests take a temp database that is closed before
removal (Windows refuses to unlink an open file, which failed the first
attempt on cleanup rather than on the assertion).

Verified: 8/8 admin tests pass, and `apps/admin/data/` does not reappear after
a full suite run.

## Note on the browser harness

`form_input` sets `.value` directly, which React does not see — one login
silently did nothing, with no request sent and no error shown. Reliable input
goes through the prototype's value setter plus a bubbled `input` event. Worth
knowing before reading a future "login failed" as an application fault.

## Residual risk

- **No test guards the loop.** The fix is a `useRef` convention in three files;
  a fourth screen written the same way would reintroduce it and nothing would
  fail. A render-count or fetch-count assertion would be the real fix.
- `organization/index.tsx` also builds `texts(...)` per render but does not
  list it as a dependency. Correct today, one careless edit from not being.
