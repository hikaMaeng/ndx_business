# Regression tests for the render loops — execution report

- **When**: 2026-08-29 00:20 KST
- **Verdict**: **PASS.** Guards in place and proven in both directions. Writing
  them found that one of yesterday's two fixes was wrong, and a third defect beside it.

## The tests

`node --test` with jsdom, mounting the real components. Deliberately not a lint
rule over dependency arrays: the defect is behavioural — an effect re-running
after its own render — so the tests count requests, which is the only thing that
revealed it in production either.

| File | Guards |
| --- | --- |
| `src/front/shell/index.test.tsx` | the shell resolves its user once; re-rendering does not re-authenticate |
| `src/front/account/index.test.tsx` | a failed load is not retried in a loop |
| `src/front/i18n.test.ts` | every bundle carries the same keys, and every key the code renders exists |

Admin's suite goes from 8 tests to 13.

## Proven in both directions

A passing test proves nothing until it fails on the defect. The shell fix was
reverted and the suite re-run:

| | fixed | defect reintroduced |
| --- | --- | --- |
| shell: asks once | pass | **fail** — "saw 26 calls to /api/auth/me" |
| shell: re-render | pass | **fail** |

The first attempt hung for the runner's full five-minute timeout instead of
failing: a runaway loop is fed by its own resolved promises, so answering them
forever means the assertion is never reached. The stub now stops answering past
25 identity calls, turning the hang into a 146 ms failure whose message names
the cause.

The second test initially passed *with the defect present* — the mount was
already looping, so the delta it measured was small for the wrong reason. It now
checks the mount count before measuring the delta.

## What writing the tests found

### 1. The account fix was wrong

Yesterday's commit said the account screen's retry storm came from unstable
translations in the dependency array. **It did not.** With those removed, the
test still recorded 26 attempts. The real driver:

```tsx
}, [model, request, snapshot.status, token]);  // status is a dependency
  .catch(() => { current.status = "idle"; });  // failure resets it
```

`idle` means "nobody has tried yet" — precisely the condition the load waits
for. Putting a failure back into it *is* a dependency change, so the effect
re-fires at once. The status union had no failure state, so a failure had
nowhere else to go.

Fixed by adding `failed` to the union in `admin_domain`. Only a deliberate retry
returns the screen to `idle`, and there is now a **Try again** control to do
that, added to all eight locale bundles.

### 2. The i18n contract did not exist

`i18n.ts` carried a comment saying `check-i18n.sh` fails the build if the bundles
diverge. No such script is in the repository, so nothing enforced it. A key added
to one bundle and forgotten in seven would have shipped as a blank label. There
is a test now.

### 3. Every restart was corrupting-adjacent

Unrelated to the loops, found in the logs while verifying: every admin restart
began `database system was not properly shut down; automatic recovery in progress`.

The entrypoint sent `TERM` to postgres. To postgres, `TERM` is *smart* shutdown:
refuse new connections, then wait for existing clients to leave on their own. The
admin server beside it holds a pool, so that wait never ended, docker's ten-second
grace expired, and the database was killed mid-write.

Now `INT` (fast shutdown) with a 60s grace period, which the host bind mount wants
regardless. Measured after the change:

```
LOG:  shutting down
LOG:  checkpoint starting: shutdown immediate
LOG:  checkpoint complete: wrote 112 buffers ... total=0.166 s
LOG:  database system is ready to accept connections
```

No recovery line. Restart takes 5.5s. 117 sessions and 28 users intact across it.

## Residual risk

- **The guard is per-screen.** Three components are covered; a fourth written the
  same way is unguarded until someone writes its test.
- **The retry control is untested in a browser.** Its unit test proves the loop
  stops; nobody has clicked the button against a real failing server.
- **jsdom is not a browser.** These would not catch a layout or CSS fault and do
  not replace the DOM measurements taken against the deployment.
