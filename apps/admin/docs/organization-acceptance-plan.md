# 조직·마스터 관리자 인수테스트 계획

## 목적

다수 계정으로 다중 루트 조직, 계층 조직, 중복 소속, 책임자 권한 범위,
환경변수 기반 마스터 관리자 제한을 실제 HTTP·SQLite 경로에서 검증한다.
테스트는 운영 `admin_data` 볼륨이 아닌 별도 임시 DB에서 실행한다.

## 테스트 계정

| 계정 | 용도 |
| --- | --- |
| `hika00@gmail.com` | 마스터 관리자. `MASTER_ADMIN_EMAILS`에만 등록 |
| `org.owner@example.com` | 조직 A의 하위 트리 책임자 |
| `node.owner@example.com` | 조직 A-1의 노드 책임자 |
| `shared.member@example.com` | 여러 조직에 중복 소속되는 일반 멤버 |
| `other.member@example.com` | 권한 없는 일반 멤버 |
| `pending.member@example.com` | 승인 대기 또는 거부 검증용 |

모든 계정은 테스트 전용 비밀번호를 사용한다. 비밀번호와 세션 토큰은
증거 파일에 기록하지 않는다. 회원가입 정책이 `auto`가 아니면 마스터
관리자로 먼저 승인한다.

## 사전 조건

1. 테스트 전용 SQLite 경로를 지정한다.
2. Compose 환경에 다음 값을 설정한다.

   ```text
   MASTER_ADMIN_EMAILS=hika00@gmail.com
   ```

3. `MASTER_ADMIN_EMAILS`에 다른 테스트 계정을 추가하지 않는다.
4. 각 계정으로 회원가입 후 로그인하여 토큰을 별도 변수에 보관한다.
5. `GET /api/auth/me`에서 `hika00@gmail.com`만 `isMasterAdmin=true`인지 확인한다.

## 시나리오

### O-01 다수 계정 생성 및 로그인

1. 위 6개 계정을 생성한다.
2. 각 계정으로 로그인한다.
3. 각 토큰으로 `/api/auth/me`를 요청한다.

기대 결과: 활성 계정은 `200`, 이메일과 사용자 ID가 서로 다르며,
마스터 플래그는 `hika00@gmail.com`에만 설정된다.

### O-02 여러 루트 조직 생성

마스터 토큰으로 다음 조직을 생성한다.

```text
본사       parentId=null
연구소     parentId=null
영업본부   parentId=null
```

기대 결과: 세 조직이 모두 생성되고 각 조직의 `parentId`가 `null`이다.
한 루트가 다른 루트의 자식으로 자동 합쳐지지 않는다.

### O-03 계층 조직 생성

마스터 토큰으로 다음 구조를 생성한다.

```text
본사
├─ 개발본부
│  └─ 플랫폼팀
└─ 운영본부
```

기대 결과: 각 `parentId`가 정확히 지정되고, 조직 목록에서 동일한 노드가
중복 생성되지 않는다.

### O-04 한 멤버의 중복·다중 소속

`shared.member@example.com`을 다음 조직에 할당한다.

- 본사
- 플랫폼팀
- 연구소

기대 결과: 세 개의 조직 멤버십이 모두 존재한다. 하나의 멤버가 다른
조직에 소속되어 있다는 이유로 기존 소속이 삭제되거나 거부되지 않는다.
동일 조직에 다시 할당하면 중복 행이 생기지 않는다.

### O-05 책임자의 노드 단위 권한

1. 마스터가 `node.owner@example.com`을 플랫폼팀 책임자로 `scope=node`로 지정한다.
2. 해당 책임자로 플랫폼팀의 자식 조직 생성 또는 멤버 할당을 시도한다.
3. 플랫폼팀 자체의 멤버 할당을 시도한다.

기대 결과: 플랫폼팀 자체 작업은 성공하고, 하위 조직 작업은 거부된다.
다른 루트인 연구소에 대한 작업도 `403`이다.

### O-06 책임자의 하위 트리 권한

1. 마스터가 `org.owner@example.com`을 개발본부 책임자로 `scope=subtree`로 지정한다.
2. 책임자로 플랫폼팀 생성, 플랫폼팀 멤버 할당, 하위 책임자 지정을 수행한다.
3. 본사 또는 운영본부에 대한 작업을 시도한다.

기대 결과: 개발본부와 그 모든 하위 노드의 작업은 성공하고, 책임 범위
밖의 본사·운영본부 작업은 `403`이다.

### O-07 책임자의 책임자 임명 위임

`org.owner@example.com`이 자신의 하위 트리 안에서
`node.owner@example.com`을 플랫폼팀의 노드 책임자로 지정한다.

기대 결과: 위임은 성공한다. 이후 `node.owner@example.com`은 플랫폼팀만
관리할 수 있고, 개발본부의 다른 자식이나 상위 노드는 관리할 수 없다.

### O-08 일반 멤버 권한 거부

`other.member@example.com`으로 조직 생성, 멤버 할당, 책임자 지정을 각각
호출한다.

기대 결과: 모든 변경 요청이 `403`이며 조직 목록과 멤버십이 변하지 않는다.

### O-09 마스터 관리자 제한

1. 일반 계정으로 마스터 관리자 지정 API 또는 계정 설정 변경을 시도한다.
2. 책임자가 자신의 권한 밖 조직의 책임자를 지정하려고 시도한다.
3. `MASTER_ADMIN_EMAILS`를 DB 또는 일반 계정의 요청 payload로 바꾸려 한다.

기대 결과: 일반 계정의 마스터 지정은 불가능하다. 마스터 이메일 목록은
DB 설정이나 요청 본문으로 변경되지 않고, 오직 Compose 환경변수에서만
읽힌다.

### O-10 환경변수 다중 마스터

격리된 재시작에서 다음처럼 지정한다.

```text
MASTER_ADMIN_EMAILS=hika00@gmail.com,second.master@example.com
```

두 계정이 모두 `isMasterAdmin=true`인지 확인한다. 환경변수에서 두 번째
이메일을 제거하고 재시작하면 해당 계정은 더 이상 마스터 권한을 갖지
않아야 한다. DB 조직 데이터는 유지되어야 한다.

## API 증거

각 단계마다 다음을 저장한다.

- 요청 method/path와 민감정보를 제거한 body
- 응답 status와 응답 body
- 조직 목록의 `id`, `name`, `parentId`
- 멤버십과 책임자의 `organizationId`, `userId`, `scope`
- 실패 단계의 주체 계정과 권한 범위

출력 위치는 `test/YYYYMMDD/<HHMMSS>_organization-acceptance/`로 한다.

## 합격 기준

- 루트 조직을 여러 개 생성할 수 있다.
- 조직은 트리 구조를 유지하면서 하위 노드를 여러 단계 생성할 수 있다.
- 한 멤버는 조직 수와 관계없이 여러 조직에 소속될 수 있다.
- 노드 책임자는 정확히 해당 노드만 관리할 수 있다.
- 하위 트리 책임자는 해당 노드와 모든 하위 노드를 관리할 수 있다.
- 책임자는 자신의 권한 범위 내에서만 책임자를 임명할 수 있다.
- 마스터 관리자는 `MASTER_ADMIN_EMAILS`에 지정된 계정만 해당한다.
- 일반 계정은 마스터 관리자를 지정하거나 환경설정을 변경할 수 없다.
- 운영 DB·운영 Compose 볼륨은 테스트 중 변경되지 않는다.
